# Passage Validator Upgrade — `v3.0.0` (Cosmos SDK v0.47)

Coordinated chain upgrade on **passage-2 mainnet** from `v2.6.0` (Cosmos SDK v0.45.16) to
`v3.0.0` (Cosmos SDK v0.47.13), **governance proposal #22**. SDK upgrade engineered & fork-tested
by Crypto Dungeon.

> ⚠️ **Two upgrade proposals are in voting — follow proposal #22 (`v3.0.0`).**
> Proposal **#21** (`3.0.0`, no "v") does **not** match the on-chain handler and carries a
> mismatched checksum — do **not** configure your node for it. The correct upgrade name is
> **`v3.0.0`**, exactly as shown below.

## 2 · What changes (and what doesn't)

This is an SDK **v0.45 → v0.47** migration. At the upgrade height the chain halts and the `v3.0.0`
handler runs automatic state migrations:

- **x/consensus created** — consensus params migrate out of `x/params` into the new module.
- **Governance → gov v1** — legacy v1beta1 proposals continue to work via the compat path.
- **IBC 07-tendermint** client migration runs automatically.
- **CometBFT 0.37.5 → 0.37.18** — includes the Tachyon (CSA-2026-001) security patch. Same minor
  line, so **no `config.toml` changes are required**.

> ✅ **CosmWasm contracts are preserved.** wasmd / wasmvm are unchanged across this upgrade. A
> real-state fork-test against a passage-2 snapshot confirmed all deployed code hashes are
> bit-identical and every contract's state is intact after the upgrade. The `x/claim` custom module
> is preserved.

## 4 · Method A — Cosmovisor (recommended)

Cosmovisor swaps the binary automatically at the halt height. **The upgrade directory name must be
exactly `v3.0.0`** (with the "v") — it must match the on-chain plan name.

```bash
mkdir -p $DAEMON_HOME/cosmovisor/upgrades/v3.0.0/bin
cp /path/to/passage $DAEMON_HOME/cosmovisor/upgrades/v3.0.0/bin/passage
$DAEMON_HOME/cosmovisor/upgrades/v3.0.0/bin/passage version    # 3.0.0
```

Recommended environment:
```
DAEMON_NAME=passage
DAEMON_HOME=<your ~/.passage>
DAEMON_ALLOW_DOWNLOAD_BINARIES=false   # pre-stage manually; don't auto-download
DAEMON_RESTART_AFTER_UPGRADE=true
```

> **Gotcha (important):** if your node previously upgraded **without** cosmovisor, a stale
> `$DAEMON_HOME/data/upgrade-info.json` from the last upgrade will make cosmovisor try to "upgrade"
> on every `start` (it shuts down and backs up the data dir on boot). Before switching the service
> to cosmovisor, **remove/stash that stale file** and point `current` at your active upgrade:
> ```bash
> mv $DAEMON_HOME/data/upgrade-info.json $DAEMON_HOME/data/upgrade-info.json.stale  # if present
> ```
> Cosmovisor will write a fresh one automatically when the real v3.0.0 upgrade fires.

## 5 · Method B — manual swap

1. Node halts at **19,807,986** with `ERR UPGRADE "v3.0.0" NEEDED`.
2. Stop the service: `systemctl stop passage` (or your unit name).
3. Replace the `passage` binary on your `PATH`; confirm `passage version` → `3.0.0`.
4. Start the service: `systemctl start passage`. Watch logs for the migrations + the first block past the height.
